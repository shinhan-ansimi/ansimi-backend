# 실제 데이터 검증 리포트 (이슈 #12)

AI 실데이터가 적재된 뒤, `docs/test_routes.json`의 20개 경로로 `/api/routes/recommend`를
실제 호출해 그 결과를 이 표에 채운다.

실제 시범 지역(강남구, 이슈 #27)이 확정된 뒤 `docs/test_routes.json`을 그 지역 기준으로
재생성했고, 이 리포트는 그 좌표로 실제 `risk_grid.geojson`(159,264행)을 적재한 뒤의
결과다.

## 실행 방법

1. AI 실데이터가 `risk_grid`에 적재되어 있고, `service_area`가 확정된 지역으로 설정되어
   있는지 확인한다.
2. `docs/test_routes.json`의 각 경로(`origin`/`destination`)로
   `POST /api/routes/recommend`를 순서대로 호출한다.
3. 매 호출의 응답(`candidates`, `recommendedIndex`)과 `route_request.elapsed_ms`를
   아래 표에 채운다.

## 참고

- 이슈 #25에서 mock 데이터(159,253행) 기준 성능은 이미 확인함 — 평균 374ms, 최대
  1072ms(`docs/risk_grid_perf_check.md`). 실데이터(159,264행)로 교체한 뒤도 평균
  203.7ms·최대 426ms로 그 범위를 벗어나지 않음.
- **실데이터 등급 분포가 RED 쪽으로 많이 치우쳐 있음**: `risk_grid` 적재 결과
  `RED=88,901(55.8%) / YELLOW=66,869(42.0%) / GREEN=3,494(2.2%)`. 현재
  `app_config`의 등급 기준값(`level_yellow_min=60`, `level_red_min=85`)은 dev 가짜
  데이터 기준으로 잡아둔 값이라, 실데이터에서는 절반 이상이 RED로 분류된다. 이번
  20개 테스트에서도 추천 결과의 절반 이상이 RED로 나왔다(아래 표). 추천 로직
  자체의 버그는 아니지만, 등급 기준값을 실데이터 분포에 맞게 재조정할지는 별도
  논의가 필요해 보인다(이슈 #28 LightGBM 채택 논의와도 연결될 수 있음).
- 일부 경로는 직접 걸어보며 색상 구간(GREEN/YELLOW/RED)이 체감과 맞는지 판단이
  필요하다(개발 명세 1장 HITL).
